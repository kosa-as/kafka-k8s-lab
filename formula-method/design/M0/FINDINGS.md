# M0-R2 反例与缺陷候选

**本轮未确认新的 Kafka 或 Kubernetes 源码实现缺陷。** 已确认的是旧模型中的抽象错误与遗漏，并在修正后找到跨层健康契约不成立的路径、结果判断容易误用的路径。当前只做前期模型验证，未进行实机故障注入。每个结论均受 [模型约束](DESIGN.md) 限制。

PAT 最终共有 43 条断言：34 VALID、9 NOT valid。其中 9 条失败分为五条候选健康契约、三条错误结果推断和一条调度负对照。网络可达性盲区另外通过强可达性见证 N01/N03 说明，不能按失败条数计算缺陷数。

## 九条 NOT valid 分别是什么

| ID | 被反驳的要求 | 实际含义及分类 |
|---|---|---|
| H06 | 每个 Pending 操作无条件最终结束 | 调度可以永远不运行客户端；是无公平性的负对照，不能指称线程死锁 |
| B02 | Ready 必须代表 Broker 请求处理已启用 | Controller TCP 可以较早成功；候选启动观测空窗，尚无秒级/实机证明 |
| N04 | Producer 超时必须代表记录未提交 | 记录提交与客户端收到成功结果不同；结果语义误用 |
| E02 | Liveness 成功必须代表请求执行可推进 | pgrep 只观察进程；在假设的局部执行停滞下出现探针盲区 |
| D02 | Ready 必须代表存储可推进 | Controller TCP 不执行目标分区存储 I/O；在假设的磁盘停滞下出现盲区 |
| R04 | Ready 必须代表目标分区满足 minISR | TCP 探针不查询分区副本条件；复制故障、追加和超期未追平后可不满足 |
| R05 | Broker 错误响应必须代表选中记录未提交 | AFTER_APPEND 判定可能在 HW 已覆盖记录之后返回错误；结果语义误用 |
| Q03 | NotReady 之后不能再完成业务成功 | 已有连接上的在途请求仍可能成功；反向健康契约过强 |
| F06 | Poll 空结果必须代表 Broker 无数据 | 网络阻断或 poll 期限可导致当前调用拿不到已有数据；结果语义误用 |

每一条的精确公式、预期和实测见 [VERIFICATION.md](VERIFICATION.md)。完整原始路径见 [TRACES.md](TRACES.md)；下文箭头链为真实路径的关键事件摘录，不是毫秒时间线。

## 1. 客户端链路故障可以同时绕过两种探针

N01 中，客户端到 Broker 的请求/响应链路中断，但 Kubelet 到 Controller 的 TCP 路径正常，Kafka 进程也仍存在。客户端可以超时；故障后新的 Readiness 和 Liveness 仍分别成功至少两次。这比只观察旧缓存 Ready 更强，因为路径中确实执行了新探针。

涉及的是不同网络路径，不能把 `client_net=0` 理解为全部 Kafka 网络都断开。环境假设来源是服务端和探针使用不同连接；模型没有证明某种特定网卡或网络策略一定制造该差异，也未在实机上复现。它揭示当前健康配置无法代表任意客户端视角的端到端可达性。

## 2. 已提交、客户端超时、之后才收到响应

N02/N03 的被动观察器要求：**选中记录已经提交，Broker 已形成成功响应，调用仍 Pending，交付期限尚未到达，而且响应链路处于中断状态**。随后观察超时；N03 还要求超时时链路仍然中断，之后才恢复并送达响应。这样排除了“客户端早已超时、后来才提交”的弱路径。

关键顺序为：

```text
c_begin → b_accept → fe_client_cut
→ b_dispatch → b_io_begin → b_io_complete
→ 两个远端追平 → cc_high_watermark → b_produce_ok
→ observe_committed_pending_cut
→ time_client → c_poll（应用交付超时）
→ observe_timeout_during_cut → fe_recover → b_deliver
```

检查 N06 同时证明：迟到响应不会把已结束的同一调用改成成功。它是结果不确定性的模型见证，**不等于 Kafka 丢失了已经确认的数据，也不证明重复发送已经造成重复记录**。本版没有展开幂等 Producer 序号、重建客户端或应用自行重发。

源码依据是 [Sender.java](evidence/Sender.java) 对排队及在途批次的独立期限处理。业务或论文若用“最终异常”作为“Broker 没处理”的判据，会在这里误判。正确观测应分别保存提交事实与客户端结果。

## 3. 已提交的记录也可能伴随 AFTER_APPEND 错误

R03 的路径先完成选中记录的副本复制与 HW 推进；之后切断复制路径，由显式背景追加使远端落后，经过 lag 和 ISR 更新后降至 ISR=1。此时 DelayedProduce 才检查该操作：HW 已覆盖记录，但当前 ISR 低于最小要求，于是形成 `NOT_ENOUGH_REPLICAS_AFTER_APPEND`。

```text
b_io_complete → 两远端追平 → cc_high_watermark
→ fe_replica_cut → cc_background_append
→ 两远端 lag 到期及移出 ISR → b_after_append_error
```

这是 [Partition.scala](evidence/Partition.scala):1090–1125 的分支语义。R05 反驳的是“Broker 错误意味着未提交”的业务推断，并非报告 Kafka 实现违反承诺。该协议错误仍可能被 Producer 内部重试；不能把一次 Broker 错误等同于最终应用错误。

时间与调度没有展开，所以本版证明的是允许该先后关系的抽象路径，不声称它在默认超时设置下高概率出现。更没有把 ISR=1 之后的本地新追加当成允许行为；S00 保留了前置 minISR 与 HW 约束。

## 4. Readiness 失败不代表已经接收的业务必须失败

Q02/Q03 只中断 Kubelet 到 Controller 的探针路径。连续六次失败后 Ready 清除；已接收的请求与现有客户端连接仍可完成。观察器要求先出现 `ready=0、client=Pending、rx=成功`，随后客户端才得到最终成功结果，排除“先成功、后来变 NotReady”的无关历史状态。

这说明“健康状态”与“某个在途操作结果”不能双向等同。这里**没有建模 Service Endpoint 更新，也没有证明客户端还能通过 Service 向 NotReady Pod 发起新请求**：`c_begin` 本身仍以 Ready 为前提。故此不能只凭 Q02 宣称 Kubernetes 进行了错误摘流，或宣称所有新业务仍然健康。

Q01 同时给出阈值的滞后窗口，Q04 验证到六次已消费失败后 Ready 确实清除。该窗口是配置语义，不是实现违规，不能把模型事件数量直接换算成六十秒。

## 5. 有数据不代表这一次 poll 必然取得数据

F05/F06 中目标数据已存在，但客户端链路中断，poll 的本地期限先到，返回空集合。它与健康无数据场景 F03 的返回形式相同，根因不同。

源码依据是 [KafkaConsumer.java](evidence/KafkaConsumer.java):859–876 的 poll 期限语义。空集合不能单独用作“Broker 没有数据”或“业务成功”的证据。本模型不包含 rebalance、用户回调阻塞或跨 Broker 路由，因此只讨论固定已知目标的数据获取。

## 6. 重新校验旧的三个方向

- **启动 Ready 空窗**：B01/B02 仍能找到。但初始延迟、探针周期、实际启动耗时被省略，不能推出某次真实启动误报 Ready。旧 [启动日志归档](../KafkaBroker/ReadinessGapArchive-2026-10-20/README.md) 也没有证明实际 Pod 曾在客户端启用前 Ready。
- **执行/存储盲区**：E01/D01 要求请求仍等待应用结果、期限尚未过去，并出现故障后两个新 LP 成功。D03 则从仍 Pending 的 I/O 等待状态走到独立的客户端超时。执行与存储停滞仍是环境假设，没有找到造成它们的源码死锁根因。
- **副本 Ready 盲区**：R01/R02 在持续探针和明确追加前提下仍成立；不再冻结 Probe。复制故障保持控制平面可用，不直接套用到旧整 Pod 网络分区场景。完全空闲对照 I01/I02 均 VALID，说明新版不再把“断网”直接等同于“ISR 必然降至 1”。

## 7. 模型自身的质量检查

确认并修正的旧模型问题详见 [SOURCE_AUDIT.md](SOURCE_AUDIT.md) 的 A01–A09。其中多项会影响反例真实性，尤其是单 ACK 提前成功、ISR 检查与追加的原子性、空闲断网缩 ISR，以及缺失在途超时。

在临时副本中分别重新引入三个错误：仅等一个远端 ACK、允许空闲断网缩 ISR、禁止在途请求交付超时。对应安全性质、空闲负对照和公平活性性质都产生了 NOT valid，见 [变异记录](results/mutations/summary.json)。这验证性质能够检测这些具体抽象错误，不代表已经证明模型全面正确。

论文中可将这些结果表述为：“基于固定版本源码的有界模型，在明确环境假设下识别了健康状态与业务结果之间的若干不一致场景，并通过安全约束及负对照剔除部分抽象伪反例。”尚不能表述为“发现九个 Kafka/Kubernetes 源码漏洞”。
